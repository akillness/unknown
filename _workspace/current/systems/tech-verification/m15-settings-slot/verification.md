# M15 player settings survive a recovery-slot switch

## 0. What this increment is

One adversarial review pass over the playable T0/C1 runtime plus exactly one smallest
player-visible correction. In-place update inside the existing cycle (RFC-Q2: `cycle`
unchanged, so `supersedes: null` and no archive obligation).

## 1. Defect found (P2 — persistence + accessibility)

[OBSERVED] Boot always reads player settings from the save **root**
(`T0GameSession.Initialize` → `<saveRoot>/settings.json`), but `SaveSettings()` wrote them
to `Store.DirectoryPath`. The recovery overlay reassigns `Store` to a slot folder:

- `recovery-new-slot` → `Store = new AtomicSaveStore(<saveRoot>/recovery-<guid>)`
- `select-slot-{n}` → `Store = next` (the selected `<saveRoot>/recovery-*`)

After either action every settings write landed in `<saveRoot>/recovery-*/settings.json`,
which boot never reads. Player-visible symptom: once a player has recovered from an
unreadable save, **every** option silently reverts to default on the next launch.

All six writers route through that one method, so all six were affected:
`language`, `textScale`, `reducedMotion`, `holdSeconds`, `confirmMode`
(`c1ConfirmMode` / `c1SignatureConfirmMode`) and key `bindings`.

Severity rationale: text scale, reduced motion and key rebinds are accessibility
affordances, and the trigger is a reachable, already-tested path
(`T0PlayModeTests.RecoveryNewSlotIsSelectableAfterSessionRestart`). Two separately
verified contracts — settings persistence and recovery-slot selection — did not compose.

Not a defect (checked and closed during the same review):
- Developer `ValidationResult.DataDiagnostic` strings do **not** reach the player;
  `C1GameSession.PatrolDiagnostic` falls back to localized `L("unavailable")`.
- `read-original` is correctly disabled at the read budget; `ReadCount` is incremented
  only by `ReadOriginal`, matching the displayed `reads / budget`.
- `Tool` "next" dereferences `Gamepad.current`, but its only binding is
  `<Gamepad>/rightShoulder` and `Rebind` pins it to `<Gamepad>`, so no reachable
  keyboard-only null path was demonstrated. Left unchanged — no test, no claim.
